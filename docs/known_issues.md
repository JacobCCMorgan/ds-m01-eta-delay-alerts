# Known issues and supported input boundaries

These are reproducible engineering findings, not estimates of fleet failure rates. The retained synthetic run has 14,349 snapshots; its GPS and departure clock differences are whole seconds, and its telemetry records use revision 1. A passing replay of that run cannot establish behavior for other timestamps, revisions or interrupted writes.

| ID | Trigger and observed behavior | Current boundary |
|---|---|---|
| DSQ-G11 | Two telemetry revisions share a tenant and canonical event ID. The HTTP event store can retain both revisions; the warehouse key omits revision, and snapshot lineage indexes that event by tenant and event ID. | Open. Keep multi-revision telemetry outside the supported input contract until ingestion, snapshot selection, lineage and persistence agree on identity. |
| DSQ-G12 | A snapshot arrives 299.5 seconds after the selected GPS event. The historical producer stores 299 completed seconds but the original feature check expects 299.5. Elapsed departure time has the same precision boundary. | Corrected in the snapshot, warehouse, baseline-history and current feature-loading paths; three fractional-clock regression tests cover the change. The earlier whole-second replay did not exercise this case. |
| DSQ-G13 | A warehouse rebuild writes a Parquet table and subsequently rejects another table. SQL rollback cannot reverse the earlier filesystem write. Removing the old database before successful completion can also leave an incomplete rebuild. | Open. Preserve the previous complete database and Parquet set before running fault-injection or a destructive rebuild. A successful fresh rebuild does not prove recovery after failure. |

**DSQ-G11 — telemetry identity.** See [HTTP storage](../src/ds_m01/event_api.py), [snapshot assembly](../src/ds_m01/pipeline.py) and the [warehouse keys](../src/ds_m01/warehouse.py). For the M5.2 integration gate, define a versioned identity and the rule for the latest *known* revision. Send two revisions of one event through HTTP, build snapshots on both sides of correction availability, and load them into the warehouse. The first snapshot must keep its original event and lineage; the later snapshot must reference the eligible revision. Prove tenant isolation and idempotent replay for both revisions.

**DSQ-G12 — clock precision.** The supported stored representation is completed nonnegative seconds for GPS age and elapsed trip time. The source timestamps retain microseconds; apply the stale-position cutoff to the exact time difference before masking. A stored age of 900 seconds can represent either exactly 900 seconds or 900 seconds plus a fraction. The first remains usable at an inclusive boundary, the second is stale. Historical remaining-time calculations must use the known actual departure, not reconstruct it from a rounded elapsed value. This issue is separate from scoring all candidates against the same fractional remaining-time target in the model comparison.

The current feature-loader entry point is `ds_m01.feature_run.build_snapshot_feature_row`. The low-level M3b.2 replay projector was frozen with the earlier experiment; that retained source is not the current interface for arbitrary fractional clocks. The fix is exercised by `test_fractional_source_clocks_survive_snapshot_and_feature_loading` in [feature loading](../tests/test_feature_run.py), `test_history_uses_exact_known_departure_not_integer_elapsed_reconstruction` in [baseline history](../tests/test_baseline_run.py) and `test_position_age_counts_complete_seconds_not_clock_boundaries` in the [warehouse contract](../tests/test_warehouse_contract.py).

**DSQ-G13 — interrupted warehouse rebuild.** See [database creation and Parquet export](../src/ds_m01/warehouse.py) and the [fresh rebuild receipt](../reports/rebuild_report.json). For M5.2, stage complete outputs as one version, then publish only after validation. Force a failure after the first Parquet write and another after database creation; show that the old database and every old Parquet file survive together, or that documented recovery restores one complete consistent version. Rebuild once more and compare the recovered result to a clean run. This issue concerns cross-file persistence; it is distinct from the separately tested publication of source/model artifacts.
